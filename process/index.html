How I direct AI agents, and what review caught

This is the method behind the bakery build, written down after launch as a playbook: its ten rules, the loop every change runs, the incidents that turned into rules, and the first outside review of this site.

Five words this page uses

  • Orchestrator. The agent session that splits a job into pieces, writes a prompt for each piece, and checks what comes back.
  • Lane. One of those pieces: one agent in its own terminal, given its own files so no two agents edit the same one.
  • Hook. A script that runs by itself whenever an agent edits a file, and blocks the edit if it breaks a rule, such as a hardcoded color.
  • Token. A named design value, like a color or a spacing step, defined once so every page uses the same one.
  • Parity check. A script that compares the tokens in code with the ones in Figma and lists any that differ.

Ten principles fit on one page

  1. I own the what and the “done”. The agent owns the how, and shows proof.
  2. Proof means the command and its output, plus a screenshot for any screen change.
  3. The builder never grades its own work.
  4. Small steps, committed often, easy to undo.
  5. Staging first for client work; this site went live without it and the round-1 review paid for that. I do the production push.
  6. Care in proportion to risk. Words and looks get a quick check; logic, money, data and permissions get the full gate.
  7. Lean beats thorough-looking. Every doc, test and agent costs something.
  8. One job per session, started from a short brief.
  9. Know the way back before going forward.
  10. I understand the load-bearing parts: money, data and access.

Every change runs the same loop

A change starts as a brief of one page or less and ends with my word on staging. The risk decides the middle: wording and layout get my staging check; logic, money, data and permissions get a scored review. The bakery store ran this loop, and my staging check caught a pricing bug that review had passed. This site skipped the staging step: it went live the night it was built. A fresh review passes at 9/10 and gets three rounds before a change comes back to me; the bakery build, run before the playbook was written down, allowed five.

Each incident became a rule

Overlapping test runs corrupted 16 settings, so runs take a lock; an agent resolved 13 review threads, so agents now answer threads but never resolve them. And because “Understood” was once taken as yes, a session now confirms its scope in one line before acting.

The bakery retro found the process worked and cost too much: 1.09 million words of docs, and ticket prompts of 3,000 to 7,000 words. The playbook now sets budgets, including a cap of three parallel lanes; this site’s build is the one exception, running up to five at once. Review round 1, below, is the correction.

Review round 1: what four reviewers caught

After the site went live, four reviewer agents read it the way a hiring loop would: a design lead, a web engineer, a copy editor and a panel reading as Epoch AI. I read their reports alongside them. Every fix is in the pull request, one small commit per change. The first finding stands below as it was written; the other eight are summed up in three lines.

  1. The Epoch study’s premise was false. The study said Epoch’s chart cropped on a phone. That came from a headless Chrome window, which does not behave like a real phone screen. Three reviewers emulated a 390px phone and the full axis rendered. The study was re-tested with Chrome DevTools Protocol device emulation at 390×844 and now describes what that test shows: the problem is density, not clipping. On a phone, 2010 to 2026 gets the right quarter of the plot and about 90% of the dots. The drawn “before” mock-up, which showed a label Epoch’s phone chart does not draw, is replaced by the real capture.
  2. What changed in the pages. The home page opens on the product, and the commits-per-day chart moved here as Figure 1. The bakery study explains its 78-day slip as a choice, and each study names one decision, the alternative turned down, and why. The public pages now speak to every reader, not one employer.
  3. What changed in the source. Every private file-and-line citation was removed, including those in the page source, and the live store is linked. Round 1 removed the visible scaffolding but left 22 orphan files reachable by URL; round 2 deleted them, and a reference check (tools/check_refs.py) now runs on every push to GitHub and fails if a page links to a missing file or a file nothing links to stays in the site.
  4. What changed in the styles. Page styles moved into files built on the shared design values. 0 <style> blocks remain; 145 style= attributes remained and were removed in round 2. The counts are in the next paragraph.

In this site’s first review round, the agent working on CSS held the portfolio to the co-op theme’s rule: a hook, a script that runs after every CSS edit and reports any hardcoded value. Hex color literals outside tokens.css went from 108 to 0. The 968 lines of <style> CSS embedded in 10 pages went to 0 as well; they now sit in 10 page stylesheets of 869 lines, because a sheet that had been pasted four times is kept once.

Who wrote what: agents drafted this site’s words and code. Four reviewer agents and I reviewed them in this round. My own rewrite in my own voice is still to come.

Every agent in these builds started from a written prompt. One of them, annotated, shows what a prompt has to carry.

Review round 2: what changed

The same four reviewers read the site again after round 1. These are the first six fixes, one line each: what was found, and what changed. Every fix is in pull request #2.

  • Orphan files. 22 files nothing linked to were still reachable, one with private notes. They are deleted, and the reference check above now runs on every push.
  • Inline styles. The site claimed zero inline CSS while 145 style= attributes were live. They were replaced with class rules in the stylesheets.
  • The bakery outcome. The study opened on build numbers and had no result. It now opens on the first week: 45 orders and $4,091 in net sales that could not have happened before.
  • This page. It listed every failure and contradicted itself on staging and on its caps. Round 1 is now one finding and three lines, principle 5 says what happened, and each cap is stated once.
  • The chart study’s framing. “Unsolicited” marked the one data-visualization piece as a side project. The word is gone, and the study is second on the home page.
  • The home page. The first screen had an empty right half and no outcome. It now says what the bakery system replaced and what its first week did, with the product beside it.
